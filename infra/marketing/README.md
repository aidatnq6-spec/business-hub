# Marketing infrastructure (not applied)

AI Settings credentials require the same server-only `AI_SETTINGS_ENCRYPTION_KEY` secret on Vercel and the worker. Supply its Secret Manager reference through reviewed worker configuration; do not put the value in Terraform variables/state. Saving/deleting an application credential does not update Cloud Run configuration or enable generation. See `../../docs/ai-settings-setup.md`; no additional secret or infrastructure was provisioned in this implementation.

This configuration is reviewable infrastructure code, not proof of deployed infrastructure. Terraform 1.17.0 portable and Google provider 7.46.1 were used for init (backend disabled) and validate successfully, without accessing Google Cloud credentials. The provider lockfile is included. A reviewed cloud plan is still mandatory before apply. No billing account is created or linked by this configuration.

1. Confirm project ownership, enabled billing/quota, actual regional prices and the complete cost approval. Enable neither generation nor scheduler before this approval. Applying even with flags off creates resources that can have storage/build costs.
2. Use a dedicated image repository and Secret Manager secret, with reviewed API restrictions. Build the worker at repo root: `npm run marketing:worker:build`, then `docker build -f services/marketing-worker/Dockerfile -t YOUR_TAG .`. The Docker context must exclude `.env*`, `.secrets`, `.git`, `.firebase` and `node_modules` (root `.dockerignore`). Push only after approval; build/registry fees are additional.
3. Review/pin the Google provider release and image digest. Copy `terraform.tfvars.example` to an ignored real tfvars file; it contains names/references, never secret values. Select remote state/encryption/access controls before apply.
4. First deploy has `enable_generation=false`, `enable_scheduler=false`, `worker_url=""`. Obtain `worker_uri`, update `worker_url` to that exact URI and reapply while flags remain false. This avoids a self-referencing Cloud Run template; no job is allowed to run before URI/audience agree.
5. Supply outputs and identical approved model/voice/price settings to the Vercel server environment. Use a dedicated authorized server identity with Firestore/Auth access. This Terraform grants only new bucket/queue access to the existing Vercel identity; it does not grant/replace its existing database permissions or change Firebase credentials.
6. Scheduler service-agent permissions must be verified after enabling the API. Cloud Tasks service-agent permissions to mint OIDC for the task identity must also be verified. Do not grant Editor/Owner to work around errors. The task identity alone invokes the private Cloud Run service; Vercel scheduler routes verify Google OIDC themselves.
7. Configure bucket CORS for the exact app origin and PUT headers before browser direct upload; review the CORS addition before applying. Signed URL signing from ADC also needs the documented signBlob permission or approved signing identity. Never expose the bucket publicly.
8. Run integration checks and a separately approved paid benchmark. Then enable worker generation; finally set `enable_scheduler=true` only after Vercel's `MARKETING_PREPARE_JOB` and `MARKETING_NOTIFY_JOB` are configured to the predictable full names `projects/PROJECT/locations/REGION/jobs/business-hub-marketing-prepare` and `...-notify` and corresponding flags are enabled.

Use a separate private bucket: do not change IAM, CORS, lifecycle or billing of a bucket serving the user's other application. Keep existing Firestore indexes/rules/business data intact apart from reviewed Marketing authorization rules. Lifecycle deletion is intentionally absent; agree retention before deleting anything.
